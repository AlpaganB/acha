# Health monitoring and environmental data

## Repository assessment

The React/Vite workspace uses `useMission` for crew and mission-profile context, `api.ts` for requests, and browser storage for the last workspace state and queued assessments. Its production service worker caches the app shell. FastAPI exposes `/api/v1` with Pydantic validation and SQLAlchemy models backed by PostgreSQL and Alembic. The measurement and assessment routes use client IDs for safe retries. Assessment results retain their engine inputs and profile, and the backend compares applicable readings with each crew member’s recent median. The standalone Python/SQLite demo evaluates check-ins locally using the same engine.

Before these changes, the web measurement form supported heart rate, SpO₂, blood pressure and body temperature. The research endpoint replayed a PhysioNet record. The original mission profiles describe environment and equipment. The restricted mission log now records a mission code, compartment, phase and optional pseudonymous crew code. The original workspace still supports sample records and an offline assessment queue. The restricted log uses its own access checks, audit and storage rules.

## Pressure analysis and interpretation

- A six-hour exercise uses an independently scripted 5 kPa pressure decrease and recovery. Heart rate and respiratory rate rise during a separate exercise interval. SpO₂ has small variation. Ear fullness and headache are scheduled reports. This arrangement demonstrates how context changes interpretation. It has no fitted physiological parameters.
- The training detector groups consecutive five-minute steps of at least 1 kPa in the same direction. It reports initial/final pressure, net change, duration and steepest sampled rate. The 1 kPa step and 97 kPa exposure boundary are scenario settings. The sampled slope is an interval average. A clinically significant pressure change, peak rate or decompression risk cannot be inferred from the demo.
- Sampled exposure adds intervals whose two pressure readings are below 97 kPa. Threshold-crossing and missing intervals contribute zero to this sum and are unclassified for exposure. The displayed pressure coverage subtracts incomplete intervals from the selected window. No values are interpolated across missing timestamps.
- The personal reference is the median of at least five available readings per metric during the fictitious crew member’s initial rest period. Post-event medians cover transition end through 15 minutes after end, report their sample count and keep exercise visible. Differences are descriptive, with no probability or causal interpretation.
- The timeline has no treatment advice or clinical notification. Its verification prompt asks users to review values, telemetry gaps and activity. Real alarms require traceable device quality, vehicle and suit configuration, approved mission rules and medical review.

## Architecture changes and verification

- The existing measurement endpoint accepts `respiratory_rate` and returns `breaths/min`. Alembic revision `0005` extends the check constraint from the sleep-duration migration. Mission profiles can schedule all six kinds. Existing rows need no backfill. Downgrade requires removing respiratory-rate readings or schedules after export. Sleep duration stays in the measurement history and outside NEWS2 scoring.
- FastAPI adds `GET /api/v1/research/nasa-rr6-iss` with a fixed NASA source and date range, numeric/time validation, response size limits and explicit unavailability errors. Provenance is at dataset level. No research rows enter the crew tables. The Pressure page uses the existing Mission route and shell cache. The NASA fetch requires a connection and is not an offline dependency for pressure analysis. No runtime dependencies were added.
- Alembic revision `0006` adds append-only observation and audit tables. The protected routes under `/api/v1/observations` reserve writes by record scope, enforce allowed missions, normalize timestamps to UTC, assign provenance server-side, and log authorized read requests and first writes. Repeated IDs with identical input are safe on retry. Observation fields include ingestion time, collection method, device/protocol, calibration and uncertainty.
- The Mission observations view offers an offline training timeline and an authenticated log. Numeric charts plot observed points. The latest value compares with the median of at least five earlier comparable records from the loaded part of the prior 30 days. Phase medians match the location, subject, activity, device, calibration and units of the latest accepted reading. The three-reading mean uses the latest comparable observations, including irregularly spaced ones.
- Pairing uses the nearest following or simultaneous unused reading within the selected window, in the same mission, phase and location. Candidate series keep the latest device and calibration context. Pearson r is reported for at least five pairs with variation in both channels. It is descriptive. Repeated, clustered or missing observations, shared external conditions and the pairing window can bias the result. Same-location filtering can preclude actual preflight/in-flight comparisons. Phase location mappings require manual verification.
- Connected pressure analysis reports elapsed intervals of at most five minutes from comparable records. It reports the steepest sampled rate with its two readings, time and duration. For an entered review boundary, it counts sampled minutes with both endpoints below it. The threshold is selected for retrospective review. The software has no onboard operational alarm, DCS model or clinical triage logic for pressure.
- Verification on the integrated branch passed 41 backend tests, 62 standalone demo tests and seven frontend analysis tests. The populated `0004` schema retained its sleep records through upgrade to `0006` and rollback to `0004`. Browser verification covers the redesigned interface, sleep and respiratory history, research reads and offline training routes once the shell is cached.

## Restricted log setup

The public demo continues to support sample data by default. An operator can set `ACHA_PUBLIC_WORKSPACE=disabled` to disable the legacy crew and mission-profile APIs for a restricted installation. The log is disabled for every credential until `ACHA_OBSERVATION_ACCESS` is configured. Use HTTPS in deployment and generate a high-entropy access key per actor. Keep the original key out of application configuration and repository files. Store only its SHA-256 hex digest in the environment value.

```json
{
  "shift-operator": {"role": "operations", "sha256": "<64 lowercase hex characters>", "missions": ["training-a"]},
  "crew-medic": {"role": "medical", "sha256": "<a different 64-character hash>", "missions": ["training-a"]}
}
```

Operations can read and write environmental records. Medical staff can read environmental records and read/write crew records for the configured missions. Crew codes are local mission pseudonyms. They have no connection to the public workspace roster. Credential changes take effect on restart. The browser holds keys and restricted records in memory, and server responses opt out of caching. Locking or leaving the log clears its display. A local deployment keeps the restricted log available on the mission network without internet, provided its own frontend, API and database remain reachable. The browser does not keep a private offline queue.

Successful list requests and first writes are audited by actor, mission, scope and optional crew code. Audit entries omit the health value and narrative. Reverse proxy and access logs can still contain route and filter identifiers. Role provisioning, database encryption, access logging configuration, backups, retention policy, individual assignment, consent and independent security review are deployment responsibilities. The application is a prototype. Use fictional data in an unreviewed environment.
